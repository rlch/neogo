Neo4j uses **labels** for nodes and **types** for relationships. neogo provides flexible ways to define and work with both.

## Node Labels

### Single Label

The simplest case is a node with one label, defined in the `neo4j` tag:

```go
type Person struct {
    neogo.Node `neo4j:"Person"`

    Name string `neo4j:"name"`
}
```

Creates nodes like:
```cypher
(:Person {name: "Alice"})
```

### Multiple Labels

Nodes can have multiple labels by listing them in the tag:

```go
type Employee struct {
    neogo.Node `neo4j:"Person,Employee,Active"`

    Name       string `neo4j:"name"`
    Department string `neo4j:"department"`
}
```

Creates nodes like:
```cypher
(:Person:Employee:Active {name: "Alice", department: "Engineering"})
```

## Label Inheritance with Embedding

Go's struct embedding creates natural label hierarchies:

```go
// Base type
type Person struct {
    neogo.Node `neo4j:"Person"`
    Name string `neo4j:"name"`
    Age  int    `neo4j:"age"`
}

// Employee extends Person
type Employee struct {
    Person                      // Embedded - inherits Node and fields
    neogo.Node `neo4j:"Employee"` // Adds Employee label
    EmployeeID string `neo4j:"employee_id"`
    Salary     int    `neo4j:"salary"`
}

// Manager extends Employee
type Manager struct {
    Employee                    // Embedded
    neogo.Node `neo4j:"Manager"` // Adds Manager label
    Department string `neo4j:"department"`
}
```

This creates a hierarchy where:
- All `Manager` nodes have labels `:Person:Employee:Manager`
- Querying `MATCH (p:Person)` returns all three types
- Querying `MATCH (e:Employee)` returns `Employee` and `Manager` nodes

## Relationship Types

### Defining Types

Relationships have exactly one type, defined in the `neo4j` tag:

```go
type Knows struct {
    neogo.Relationship `neo4j:"KNOWS"`

    Since int `neo4j:"since"`
}
```

Creates relationships like:
```cypher
-[:KNOWS {since: 2023}]->
```

### Matching Multiple Types

While relationships can only have one type, you can match multiple types in a query:

```go
// Match either KNOWS or FRIENDS_WITH
err := driver.Exec().
    Cypher(`
        MATCH (p:Person)-[:KNOWS|FRIENDS_WITH]->(other:Person)
        RETURN other
    `).
    Run(ctx, "other", &others)
```

<Aside type="caution">
When matching multiple relationship types, you cannot bind the relationship to a typed struct since the type is ambiguous.
</Aside>

## Naming Conventions

### Labels (Nodes)

| Convention | Example | Use Case |
|------------|---------|----------|
| PascalCase | `Person`, `UserAccount` | Standard (recommended) |
| SCREAMING_SNAKE | `PERSON`, `USER_ACCOUNT` | Legacy systems |

### Types (Relationships)

| Convention | Example | Use Case |
|------------|---------|----------|
| SCREAMING_SNAKE | `KNOWS`, `WORKS_AT` | Standard (recommended) |
| PascalCase | `Knows`, `WorksAt` | Alternative style |

<Aside type="tip">
Neo4j convention uses `PascalCase` for labels and `SCREAMING_SNAKE_CASE` for relationship types. neogo works with any naming convention.
</Aside>

## Working with Labels in Cypher

### Adding Labels

```go
err := driver.Exec().
    Cypher(`
        MATCH (p:Person {name: $name})
        SET p:Premium:Verified
    `).
    RunWithParams(ctx, map[string]any{"name": "Alice"})
```

### Removing Labels

```go
err := driver.Exec().
    Cypher(`
        MATCH (p:Person {name: $name})
        REMOVE p:Temporary
    `).
    RunWithParams(ctx, map[string]any{"name": "Alice"})
```

### Checking Labels

```go
var labels []string

err := driver.Exec().
    Cypher(`
        MATCH (p:Person {name: $name})
        RETURN labels(p) AS labels
    `).
    RunWithParams(ctx, map[string]any{"name": "Alice"}, "labels", &labels)

fmt.Println(labels)  // ["Person", "Employee", "Manager"]
```

## Best Practices

### Label Design

1. **Use labels for entity types**: `Person`, `Company`, `Product`
2. **Use labels for roles**: `Admin`, `Guest`, `Premium`
3. **Use labels for state**: `Active`, `Archived`, `Pending`
4. **Keep labels orthogonal**: Don't create overlapping hierarchies

### Relationship Type Design

1. **Use verb phrases**: `KNOWS`, `WORKS_AT`, `PURCHASED`
2. **Be specific**: `MANAGES` vs generic `RELATED_TO`
3. **Consider direction**: Name types so direction is natural

```cypher
-- Good: Direction makes semantic sense
(person)-[:WORKS_AT]->(company)
(manager)-[:MANAGES]->(employee)

-- Avoid: Direction is unclear
(person)-[:EMPLOYMENT]->(company)  -- Which direction?
```
